# Research result

**Status: Partial**

Auto-vectorization in safe Rust is observable on stable rustc by passing LLVM's own remark spellings through `-C llvm-args` (`--pass-remarks*`); rustc rejects the clang-style `-Rpass*` names, and its stable `-C remark` flag has a known blind spot for loop-vectorizer remarks. The dominant blockers are bounds checks and possible aliasing — both addressable in safe code by reslicing, exact-size chunking, and pre-loop assertions — while checked arithmetic, reference-yielding iterator adapters, 64-bit int-to-float conversion on AVX1/AVX2, and gather/scatter either suppress vectorization or make it slower. LLVM natively vectorizes add/mul/xor/and/or and min/max reductions (integer argmin/argmax included) but not prefix sums. The findings' measured effects favor exact-size chunking and show regressions for zip rewrites, gather/scatter, and AVX2 int-to-float vectorization; the specific case studies and toolchain options named in the query are not covered.

### Observing what the vectorizer did

LLVM exposes optimization remarks under two spellings: the Clang driver flags `-Rpass`, `-Rpass-missed`, and `-Rpass-analysis`, versus the LLVM-core options `-pass-remarks=<regex>`, `-pass-remarks-missed=<regex>`, and `-pass-remarks-analysis=<regex>` accepted by `opt` and `llc`, with diagnostics either propagated to a front end or emitted by those tools [S1]. rustc accepts only the LLVM-core spelling: `-C llvm-args=-Rpass-missed=loop-vectorize` is rejected as an unknown argument, while `-C llvm-args="--pass-remarks-missed=loop-vectorize"` (and the `--pass-remarks-analysis` form) works, and `-C llvm-args` is a codegen option that passes arguments straight to LLVM and is usable without nightly [S2].

rustc's own `-C remark` flag prints LLVM optimization remarks to stderr and carries no unstable marker in the codegen-options list (`all` remarks on every pass), whereas the YAML-writing `-Zremark-dir` is the unstable, nightly-only variant [S3]. In practice `-C remark` is unreliable for vectorization: on stable 1.87.0 and nightly, `-Cremark=all` produced nothing about vectorization and `-Cremark=loop-vectorize` reported nothing at all, while `-C llvm-args=--pass-remarks=.*` emitted lines such as `vectorized loop (vectorization width: 8, interleaved count: 4)` [S4]. `--emit=llvm-ir` is a stable emit kind that writes `CRATE_NAME.ll`, but remarks belong to LLVM's tools, so an opt-remarks workflow over the emitted IR is assembled by the user [S5].

For assembly inspection, `cargo asm` (cargo-show-asm) runs on nightly and stable and can print per-function LLVM IR (`--llvm`) or pre-LLVM-pass IR (`--llvm-input`); `cargo llvm-lines` is not a vectorization tool — it invokes `cargo rustc -- --emit llvm-ir -Cno-prepopulate-passes -Cpasses=name-anon-globals` and counts IR lines across all instantiations of each generic function for monomorphization/size analysis [S6].

### What defeats auto-vectorization

Bounds checks come first: an indexed loop like `for i in 0..z.len() { z[i] = x[i] * y[i]; }` emits two checks per iteration because it must write the correct prefix and panic in the right place if an input is shorter; reslicing all inputs to a provably in-bounds length lets LLVM unroll and vectorize [S7]. Possible aliasing is second: when two mutable slices may overlap, LLVM emits a runtime overlap check plus a scalar do-things-in-order fallback beside the vectorized loop (about 50% more assembly), and Rust's `&mut` noalias guarantees normally let it go straight to the fast path [S8].

Checked arithmetic — overflow checks that branch to a panic — has been characterized as making whole passes like loop and scalar vectorization useless, and saturating add/sub were previously costed as overflow-checked expansions until the cost model was fixed to use native saturating nodes [S9]. Vectorizing 64-bit integer-to-float conversion is often unprofitable: without AVX512DQ there is no native packed `uitofp`/`sitofp` for 64-bit lanes, which lowers to a 14-instruction scalar-through-GPR sequence, so the cost model can keep those conversions scalar [S10].

Iterator adapters that yield references are a subtle blocker: `fold`, `all`, and `max` over a slice iterator unroll but emit no vector instructions, and `.copied()` or a non-short-circuiting bitwise `&` restores SIMD, because the obstacle is poison/`noundef` propagation through reference loads — needing freeze instructions the loop vectorizer does not support — not dereferenceability [S11]. Non-contiguous accesses may be auto-vectorized into masked gather/scatter instructions that are microcoded, high-latency, and slower than scalar, so LLVM's cost model usually refuses unless forced with `-mllvm -force-vector-width=#` [S12].

### Safe code whose bounds checks elide

`chunks_exact`/`chunks_exact_mut` (stabilized in 1.31) removed every bounds check from the inner loop and stopped tracking remaining slice lengths [S13]. A `while` loop over repeated `slice::split_at` — which is what `chunks_exact` does internally — matched it closely with near-identical assembly [S14]. `zip` is context-dependent rather than a guaranteed win: std specializes slice/`Vec` zips to pick the shortest length once and iterate without per-element bounds checks, yet a `zip` + `iter().sum()` rewrite in the same benchmark was markedly slower and still carried an output-slice bounds check [S15].

Pre-loop length assertions are the portable trick for hoisting per-iteration checks — redundant asserts are eliminated just like the checks — but the payoff is usually small unless it unlocks unrolling or vectorization [S16]. The assume-style hint `core::hint::assert_unchecked` is `unsafe` (immediate UB if the condition is false) and documented as allowed to do nothing or even make the generated code slower [S17]. `repr(transparent)` and `repr(align)` are documented as layout/ABI features only — transparent matches the sole non-ZST field, align raises or leaves unchanged the alignment and pads size to a multiple of it — with no documented bounds-check-elision or vectorization effect [S18].

### Reductions, scans, and parsing for market-data kernels

LLVM's loop vectorizer detects loop-carried reduction variables and natively supports addition, multiplication, XOR, AND, and OR; FP reductions vectorize on most targets only with at least `-fassociative-math -fno-signed-zeros -fno-trapping-math`, while AArch64 and RISC-V can generate ordered reductions that preserve the exact result [S19]. Min/max scans are recognized as a special recurrence shape: `getMinMaxRecurrence` requires a two-incoming PHI in the loop header with integer or FP type, a def-use chain in which every min/max operation matches the same RecurKind (`m_UMin`/`UMax`/`SMax`/`SMin`, `minnum`/`maxnum`, `minimum`/`maximum`, `minimumnum`/`maximumnum`), FP ops with `noNaNs` and `noSignedZeros` or a restricted minimum/maximum family, and chains matched as `icmp`/`select` pairs [S20]. Tracking a best value together with its index (argmin/argmax) works only for integer min/max under a restricted multi-use pattern: the PHI may have uses outside the min/max chain only if it is the only in-loop user of the back-edge value [S21].

Prefix sums are not vectorized by LLVM as of the cited upstream report: an OpenMP SIMD inclusive scan compiled with clang 19.1.7 emits "loop not vectorized: the optimizer was unable to perform the requested transformation" while GCC succeeds, and the report remains open; the nearest supported loop-carried mechanism is a first-order recurrence (header PHI with two incoming values, preheader and single latch, "previous" value from the latch), with a TODO that memory instructions are not handled [S22]. Profitability is decided by target-independent TTI hooks — `getArithmeticReductionCost` (tree-wise for integers, and for FP only when reassociation is allowed; ordered lane-order otherwise, with `requiresOrderedReduction` true exactly when the fast-math flags disallow reassociation), `getMinMaxReductionCost`, `getPartialReductionCost` for `llvm.vector.partial.reduce.add`/`fadd`, and `isLegalToVectorizeReduction` — after which the vectorizer picks its vectorization and unroll factors from the cost model [S23].

The VPlan framework widens IR by a vectorization factor, legalizes by introducing specialized recipes for reductions and interleave groups, and forms vector idioms by pattern search; mixed-type kernels are supported with the cost model pricing type conversions, and data-dependent parse loops rely on documented control-flow support — if-conversion of arbitrary innermost-loop control flow, a single early exit handled by predicating the blocks after it, a scalar remainder for unknown trip counts, and rejection of switch statements [S24]. The findings do not specifically address packed fixed-width integer comparison or decimal-ASCII parsing to scaled integers beyond these recurrence and control-flow mechanics.

### Measured effects and case studies

| Context | Change | Measured effect |
|---|---|---|
| RGB→grayscale, 1920×1080 | `chunks`/`chunks_mut` → `chunks_exact`/`chunks_exact_mut` | 4,420,145 → 2,007,459 ns/iter, a 2.2× speedup [S13] |
| RGB→grayscale | `while` loop over repeated `slice::split_at` | 2,046,834 ns/iter vs 1,965,631 ns/iter for `chunks_exact` [S14] |
| RGB→grayscale | `zip` + `iter().sum()` | 11,393,600 ns/iter, 2.9× slower [S15] |
| Checked-multiply loop | checked vs unchecked arithmetic | ~3× slower (1085 vs 349 ns) [S9] |
| AVX1/AVX2 64-bit int→float | SLP-vectorized `uitofp` | 3.1 → 3.5 ns per call; 1.25× slower in Julia's BaseBenchmarks [S10] |
| Non-contiguous loops | gather/scatter under `-O3`/`-march=native` | >2× slower; 3.7–3.9× slower with dependent AVX2 `vpgatherdd` (rustc 1.96 / LLVM 22.1.2) [S12] |
| Hot loops with slice indexing | pre-loop length assertions | 1–3% typical, up to 15% maximum [S16] |

The pattern is uneven: exact-size chunking and `split_at` cluster at the top, plain bounds-check removal is a modest win, and several transformations that sound like vectorization wins — the zip rewrite, gather/scatter lowering, AVX2 64-bit int-to-float conversion — are net regressions. The findings contain no measured results for the Google libgav1 AV1 decoder's Rust SIMD port, simd-json, memchr, or rustc's own hot loops as case studies, and none for `-C target-cpu=native`, profile-guided optimization via cargo-pgo, BOLT, or portable SIMD `std::simd`; those parts of the query remain unverified.

- "Question 1 uncertainty: I could not run rustc/opt in this environment (read-only tools, no shell), so stable-vs-nightly gating of '-C llvm-args' and '-C remark' is inferred from the rustc book (no 'unstable' marker), the Unstable Book listing only '-Zremark-dir', and the reporter's use on stable 1.87.0 — not from a direct compiler invocation."
- "Question 1 uncertainty: Whether running the external LLVM 'opt' tool on rustc's '--emit=llvm-ir' output faithfully reproduces rustc's own vectorization decisions was not verified; rustc emits already-optimized IR by default, and '-Cno-prepopulate-passes' changes what IR is present."
- "Question 1 uncertainty: cargo asm's ability to surface vectorization remarks itself (vs. merely dumping IR/asm and passing through -C/-Z flags) was read from its README; I did not verify it emits or visualizes loop-vectorize remarks."
- "Question 1 uncertainty: The local workspace (/Users/petermager/Downloads/code/orderbook-lab/config) contains only dev.json/prod.json runtime configs with no Rust source or compiler flags, so it contributed no evidence for this question."
- "Question 2 uncertainty: The local workspace repository (orderbook-lab) contains no Rust or SIMD code and no documentation of these patterns; it could not corroborate any claim."
- "Question 2 uncertainty: No source I inspected uses the term 'unelidable bounds checks' verbatim; the bounds-check claim rests on demonstrations that specific indexing loops emit per-iteration checks that reslicing removes."
- "Question 2 uncertainty: The checked-arithmetic evidence (rust-lang/rust#9469) is a 2013 maintainer comment and microbenchmark, not a current controlled study; behavior may differ on modern rustc/LLVM, and no recent primary measurement was inspected."
- "Question 2 uncertainty: For saturating arithmetic, PR #97463 documents a cost-model bug (overestimated expansion), not a demonstrated real-world case where correct vectorization was blocked; I did not find a controlled Rust benchmark isolating saturating_add."
- "Question 2 uncertainty: The aliasing evidence is a forum post plus LLVM docs; in Rust the failure mode is the *absence* of noalias proof (raw pointers / unmarked slice pairs) that triggers loop versioning, so the claim that aliasing itself 'defeats' vectorization is only conditionally true."
- "Question 2 uncertainty: The int-to-float evidence concerns SLP profitability and a performance regression from over-vectorization (PR #230098, Oct 2026), not a clean demonstration that the cast strictly prevents vectorization; the reverse direction (saturating float-to-int, e.g. rust fptosi.sat) was mentioned in sources but not verified here."
- "Question 3 uncertainty: No inspected source claims a proof that any of these constructs elides bounds checks or restores vectorizability; the strongest support is empirical assembly/benchmark observation, not a proof, and the question's 'provably' framing overstates the evidence."
- "Question 3 uncertainty: I could not inspect the IEICE report 'A Study on Array Bounds Checking Optimization in Rust' (NS2025-188) -- the page is behind a human-verification wall -- so reported figures such as 'up to 49% speedup' are unverified."
- "Question 3 uncertainty: The standard-library docs for chunks_exact, zip, and split_at document API semantics only (exact-size chunks with a retrievable remainder; zip using the shortest length; split_at panicking if mid > len); they make no claims about bounds-check elimination or vectorization, so those effects rest on third-party benchmarks."
- "Question 3 uncertainty: Whether assertions help is placement- and macro-sensitive: the same benchmark found an inner-loop assert! left a single check and assert_eq! was ~1.1x slower than the no-assert baseline due to panic-formatting setup (4,897,046 vs 4,420,145 ns/iter); I did not verify this across compilers."
- "Question 3 uncertainty: repr(align) can in principle enable aligned SIMD loads/stores, but no inspected primary source ties repr(align) or transparent newtypes specifically to bounds-check elision or vectorizability; that link is not documented."
- "Question 3 uncertainty: Effects vary by LLVM/rustc version, target CPU, and surrounding code; Shnatsel notes automatic vectorization is 'notoriously fickle' and that codegen changed between compiler versions, and the 15% case was attributed to loop unrolling, not the bounds checks themselves."
- "Question 4 uncertainty: No source I found addresses market-data kernels (price-ladder min/max scans, cumulative depth/prefix sums, packed-integer tick comparison, or decimal ASCII price parsing) by name; the claims above are the upstream LLVM requirements such code must satisfy, not evidence that these specific kernels vectorize."
- "Question 4 uncertainty: Whether a real scan loop over a price ladder hits the min/max reduction fast path or the generic reduction path depends on exact IR shape (header PHI, chain uniformity, FMF); no source states how such memory-fed scans are classified."
- "Question 4 uncertainty: Prefix sums might be partially vectorizable in some cases via loop distribution isolating the scan (mentioned in search results) but I could not confirm this in a primary source I inspected, so I am not claiming it."

- "Question 5 uncertainty: The libgav1 2.7x figure is a vendor blog claim measured against Google's own earlier Rust port (not the C++ original); no per-kernel benchmarks, patches, or public repo for this specific optimized port were released with the announcement."
