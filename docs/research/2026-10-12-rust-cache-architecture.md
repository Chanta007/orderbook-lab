# Research result

**Status: Partial**

For a single host serving hundreds to thousands of symbols, each book should be a fixed-depth, price-ordered array or a tick-bucketed flat ring rather than a BTreeMap, which wins only in the middle of the book [S1][S2][S3]. Shard symbols across threads by hash into cache-line-padded, independently locked shards, and intern symbols once into ids, because a frozen interner is contention-free while the live concurrent interner collapses under many-thread load [S7][S10]. Move updates through bounded rings with Acquire/Release index ordering [S11], accepting that a cross-process mmap ring needs an unsafe, self-managed layout because Rust's atomics and the standard ring crates are defined for threads, not processes [S15]. Represent backpressure explicitly — window or credit gating, or a bounded ring that never overwrites unconsumed entries — with sequence-numbered gap recovery for anything dropped, and pre-size every structure so the hot path never allocates [S2][S5][S6][S16][S17][S20].

### Per-symbol book structures and measured cost

The fixed-depth array layout keeps each side as a `[Level; 200]` array in price order with the best level at the end, scanning the best 16 levels linearly and binary-searching the rest; its published medians are 122 ns per `apply_delta` at one level per side, 63 ns for `bbo`, 1.3 ns for `Side::best`, and 13.2 ms for 100,000 sequential deltas (~7.6M deltas/sec) [S2].

| Side layout (1,000-update stream, 200 levels, Haswell Xeon E3-1231 v3) | Update (best) | Add+remove at top | Add+remove mid-book |
|---|---|---|---|
| Fixed-depth sorted array | 3.93 ns | 12.1 ns | 136 ns [S1] |
| BTreeMap | 14.3 ns | 45.1 ns | 41.8 ns [S1] |

The array's advantage is confined to the top of the book and inverts in the middle: roughly 3× on the update stream and 3–4× on a top-of-book insert, paid for mid-book.

A tick-bucketed flat ring buffer serves `best_bid`/`best_ask` in ~1.20 ns and top-10 depth in ~35 ns, with single updates at ~64–71 ns at depth 20, ~21–22 ns for sparse depth-5 books, and ~152–159 ns at dense depth 50 [S3]. Slab-allocated orders report 6.29 ns for a mixed add-or-cancel, 6.74 ns per place, 4.41 ns for a mid-queue cancel, and 21.51 ns for `match_single`; a deep power-law benchmark book held a two-sided resting set of ~382 KiB, past L1 [S5]. A fixed ~33 KiB per book (~16.5 KiB per side) is sized to fit a 32 KiB L1d and does not change whether 1 or 4,000 levels are live, putting 1,000 books at roughly 32 MiB of hot data [S4].

### Sharding a thousand symbols across threads

DashMap shards by static hash partition rather than being one lock-free structure: each key's hash selects one of a power-of-two number of independently locked, cache-line-padded shards, each an `RwLock` around a hashbrown table, with a default shard count of `next_power_of_two(available_parallelism × 4)` [S7]. Cache-aligning the shard locks improved latency and throughput by 30–50% on an M2, at the cost of roughly doubling the empty map's size — a constant increase that does not scale per inserted element [S8].

| Map (98% read / 1% insert / 1% remove, Apple M1 Pro) | 1 thread | 10 threads |
|---|---|---|
| DashMap (sharded locks) | ~14.9M ops/s | ~63.9M ops/s [S9] |
| SccMap (lock-free) | ~8.3M ops/s | ~62.8M ops/s [S9] |
| Flurry (lock-free) | ~7.5M ops/s | ~58.0M ops/s [S9] |

The sharded design's lead over the lock-free maps is roughly 1.8× at one thread and narrows to near parity by 10 threads.

Interning pays off when it is frozen: a threaded interner (two DashMaps over a lock-free arena) resolves at ~1.15 GiB/s on one thread but collapses to ~98.7 MiB/s at 24 threads, whereas a frozen interner resolves at ~13.2 GiB/s single-threaded and still ~6.1 GiB/s at 24 threads with contention-free access — so intern symbols at onboarding and hand hot threads a read-only resolver and interned ids [S10].

### Lock-free queues, memory ordering, and mmap shared memory

A SPSC ring buffer orders its read and write indices with Acquire loads and Release stores and guards single-producer/single-consumer access with AcqRel swaps on hold flags — ringbuf's `SharedRb` implements exactly this, framed as CPU-cache synchronization between threads [S11]. The bounded MPMC `ArrayQueue` in crossbeam-queue, after Vyukov, is heavier: Relaxed head/tail loads in the fast path, Acquire loads and Release stores on each slot's stamp, SeqCst compare-exchange on head and tail, and an explicit SeqCst fence when a slot is not yet ready, with SeqCst loads in `is_empty`/`is_full`/`len` [S12]. The queue ships no loom model tests or loom dependency — only conventional threaded tests — so its ordering argument is not machine-checked in the repository [S13].

A seqlock gives the cheapest reader path: the writer stores the counter Relaxed and issues a Release fence before touching data, then stores Release at the end; the reader loads Acquire, reads the data volatilely, issues an Acquire fence, re-loads the counter Relaxed, and retries on mismatch — supported only for `Copy` types [S14].

memmap2 hands back raw mapped byte slices with no atomic or ordering semantics, and every file-backed constructor is unsafe because concurrent modification of the file — in or out of process — can cause undefined behavior [S15]. Rust's atomics are defined for threads, and none of rtrb, ringbuf, or crossbeam-queue documents cross-process use (rtrb's ring sits on a process-local `Vec` allocation), so a cross-process SPSC or MPSC pair over a mapping needs an unsafe, self-managed layout; ringbuf alone supports reconstruction over externally provided memory via unsafe `SharedRb::from_raw_parts` and a pluggable `Storage` trait, though its indices live inline in `SharedRb`.

### Backpressure and loss policy in the fan-out

Aeron represents backpressure as a temporary refusal: when a publisher gets too far ahead of subscribers, non-blocking `offer`/`tryClaim` fails with BACK_PRESSURED (−2) and the application must retry; enforcement is window-based (publication term window plus receiver window), and the default multicast flow-control strategy is 'max', so the fastest receiver sets the pace and a slow receiver's image eventually goes unavailable and restarts at the latest position in the stream [S16]. The LMAX Disruptor instead guarantees that a bounded ring never overwrites unconsumed entries: its sequencer requires that no downstream consumer's sequence fall below the buffer sequence minus the ring size, tracking only the leaf nodes of the dependency graph, so a lagging consumer stalls producers rather than losing data [S17].

Ultra Messaging's TCP transport offers three explicit fan-out policies: the default 'normal' mode is receiver-paced (the source blocks or returns LBM_EWOULDBLOCK when a receiver's socket buffers fill); 'source_paced' drops messages for receivers whose socket buffers are full, causing unrecoverable loss for the slow receiver while fast receivers might get all messages; and the deprecated 'bounded_latency' mode sends as fast as the fastest receiver and discards data headed for slower receivers to bound latency [S18]. Its persistence layer makes the same choice explicit: default source-paced persistence is a circular repository that overwrites the oldest messages when full — a receiver behind by more than the repository size suffers unrecoverable loss — while receiver-paced persistence blocks the source when the repository is full of unacknowledged messages [S19].

Exchange multicast feeds handle loss without any consumer backpressure: every MoldUDP64 downstream packet carries a session, an 8-byte sequence number for the first message, and a 2-byte message count, and a receiver that detects a gap sends a Request Packet (session, sequence number, requested count) to a re-request server that retransmits, with message count 0x0000 marking heartbeats and 0xFFFF end-of-session [S20].

Credit-based flow control is the link-by-link alternative: the receiver allocates buffer space (`Buf_Alloc`) and the sender tracks a balance `Cr_d_Bal = Buf_Alloc − (Tx_Cnt − Fwd_Cnt)`, stopping when credits are exhausted; it guarantees no cell loss due to congestion, minimizes delay, and suits bursty traffic, whereas rate-based schemes may need cheaper hardware and work for smooth traffic but handle bursts poorly [S21].

### Keeping the hot path allocation-free

Allocation avoidance is structural: the fixed-depth array layout performs no allocation on the update path [S2], and slab-allocated books pre-size 32-byte order nodes — two per 64-byte cache line, one slab per side — so placement and cancellation reuse slots instead of calling the allocator [S5]. The slab crate recommends sizing up front with `Slab::with_capacity` to avoid reallocation; it documents a `Vec` of occupied and vacant slots with a linked-list freelist of vacant slots but publishes no ns- or byte-level figures [S6].
